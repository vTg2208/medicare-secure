# Database transport and responder delivery

Production startup now requires `DB_SSL=true`. Clients verify the issuing CA and hostname with TLS 1.2 or newer. `DB_SSL_CA_FILE` loads a mounted public CA; existing escaped `DB_SSL_CA` remains supported. Missing configured CA files fail closed. Development and disposable integration fixtures may use plaintext.

The production Compose template requires operator-supplied `POSTGRES_TLS_CERT_FILE`, `POSTGRES_TLS_KEY_FILE` and `POSTGRES_TLS_CA_FILE`. The PEM server chain must have SAN `DNS:postgres` and an appropriate validity period. Keep private keys outside this repository. The wrapper copies the key to a postgres-owned 0600 tmpfs file, enables TLS and rejects **all plaintext TCP** connections. Local Unix-socket trust is restricted to the database container for official initialization tooling; do not grant untrusted workloads container access. The API and migration service receive only the public CA. Rotate certificates through an operator-reviewed database restart and verify readiness. No private network connection is exempt from this template's TCP policy.

Backup operators use `DB_SSL=true` and `DB_SSL_CA_FILE`/`PGSSLROOTCERT` with `verify-full`. Remote backups and disposal must not disable certificate verification. Run the existing encrypted backup and restore procedures in [backup recovery](backup-recovery.md); coordinate stopped writes, schedule off-host retention and reconcile approved disposals after restore. A schedule or restore in the actual hosting environment still requires owner execution.

Every inserted high/critical security event (including breach reports and emergency activation) transactionally creates a generic in-app notification for active compliance officers and system administrators. Escalation is idempotent. It includes only an incident ID, never the clinical narrative, and is available through each responder's authenticated notification inbox. The protected incident queue is the review destination. Persistence failure aborts the event transaction. These are internal alerts, not evidence of notifying a regulator or patient. External on-call delivery still requires the reviewed Alertmanager receiver and a delivery drill described in [monitoring readiness](monitoring-readiness.md).

Verification uses an offline disposable PostgreSQL server and an ephemeral synthetic certificate: a trusted connection reports encrypted TLS, while untrusted CA, wrong hostname and plaintext connections fail. `backend/tests/database-tls.integration.test.js` is opt-in (`RUN_TLS_TESTS=true`, test mode, loopback, explicit test CA) and never targets production. Responder integration tests cover private inbox ownership, transaction rollback and duplicate escalation. No real alerts were sent.

References: [PostgreSQL TLS](https://www.postgresql.org/docs/current/ssl-tcp.html), [PostgreSQL authentication rules](https://www.postgresql.org/docs/current/auth-pg-hba-conf.html), [node-postgres TLS](https://node-postgres.com/features/ssl).

Production SMTP also requires verified TLS (implicit TLS or STARTTLS), preventing opportunistic plaintext fallback to the configured relay. This protects the application-to-relay connection, not every downstream email hop. Transport configuration is pinned by an offline regression; real SMTP delivery still needs the intended relay drill. See [Nodemailer SMTP options](https://nodemailer.com/smtp).
