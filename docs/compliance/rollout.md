# Notice rollout and verification

This is the operator procedure. The implementation phase used disposable databases; the subsequent authorized release applied migration 033 and verified demonstration-only publications, acknowledgement, history, export and coordinated recovery on 2026-11-02. See the [live release record](../releases/2026-11-02-privacy-notices-live-release.md). The user authorized synthetic demonstration content for that verification; step 5's real-use notice review remains pending. Do not rerun the migration or publish duplicate fixtures just to repeat the release.

1. Review [operational-assurance.md](operational-assurance.md), confirm the intended installation and record its revision and exact migration ledger. Preserve the original application and independent archive keys through the existing protected recovery process. Take and successfully recover a coordinated database/upload backup before changing the installation. A downloaded artifact alone is not a successful recovery.
2. Confirm the existing ledger is exactly migrations 001–032 with matching hashes. For the existing private `healthcare` schema, generate the guarded incremental SQL from the repository root with `node backend/scripts/export-browser-upgrade.js --from 032 --output .local/browser-upgrade-032-to-033.sql`. Review the generated transaction, including grants, before applying it using the existing migration-owner workflow. It checks the full ledger, serializes migration and rejects partial/hash-drift states. Exact target-ledger replay is a no-op. Do not run the fresh-schema bootstrap against an existing installation. Public-schema installations use the existing ordered migrator rather than this private-schema exporter.
3. Verify 033's recorded hash, three new tables and the singleton pointer with a null `version_id`. Existing clinical rows and all prior migration hashes must remain unchanged. No public notice or acknowledgement should have been seeded. Verify effective API SELECT and column-level INSERT/UPDATE grants, database-generated time/hash/version fields, no notice/history UPDATE/DELETE/TRUNCATE and backup SELECT-only access. Verify `anon`/`authenticated` have no direct table access. Migration 033 handles existing restricted roles; the updated private-schema grant template handles provisioning those roles later. Test actual restricted-role operations, including immutable history rejection, rather than relying on table ACL display alone.
4. Deploy the matching API and frontend after the additive migration. Before publication, `/api/notices/current` must return the explicit unconfigured state and `/privacy-notice` must explain it. Existing authentication, care and consent flows must remain accessible. Check anonymous current/historical reads, denied anonymous receipts and denied non-officer publication. No endpoint should expose publisher identity or the private encrypted review basis publicly.
5. The responsible organization supplies accurate operator/contact facts and all nine notice sections. An authorized compliance officer reviews the preview, enters the private publication review basis, explicitly confirms authority and publishes through `/compliance/notices`. Record that human review separately from software test evidence. Do not publish fixture copy or placeholder contacts. Publishing creates an immutable version and audit event together.
6. Using approved synthetic accounts in a suitable verification environment, explicitly acknowledge the displayed current notice as a patient. Verify an owned receipt, exact version/hash/content in history and patient export, unchanged consent grants, idempotent retry and stale-version conflict after a subsequent publication. Verify a different patient's history remains inaccessible. Viewing a notice must create no receipt. Preserve old publications and receipts.
7. Run a coordinated backup/download/recovery drill after publication using the existing gated workflow. Check the migrated ledger, audit chain, notice/receipt ownership, exact historical content/digest and private review decryption with the original application key in the protected recovery environment. Test referenced uploaded files as well. Do not give the application key to the cloud backup worker.
8. Record the actual deployed revision, review attribution, verification results and remaining provider/organization responsibilities in protected operator evidence and the control matrix. Acknowledgement receipts establish what was acknowledged, not lawful processing, consent or certification.

If application rollout fails, stop publication and revert application code through the normal deployment process. Leave additive tables/history and the migration ledger intact; do not reverse this migration by deleting evidence or editing published notices. Rehearse any disaster recovery promotion separately before authorizing it for real use.
