# Coordinated database and uploaded-file backups

`npm run backup:coordinated -- /protected/output.shmsbkp` captures the application schema and its referenced encrypted uploads without an operator claiming writes have stopped. Configure the explicit database settings, BACKUP_DATABASE_SCHEMA, an **absolute UPLOAD_PATH on the real persistent application volume**, a separate BACKUP_ENCRYPTION_KEY, and either ENCRYPTION_KEY or BACKUP_APPLICATION_KEY_SHA256 for key separation. This command loads no dotenv file and accepts no secret arguments.

## Coordination

All shipped application file writers, rollback cleanup, credential storage, quarantine moves, applied encryption migration and retention-file cleanup acquire the shared PostgreSQL advisory lock `(1734962500, 1)`. Backup acquires its exclusive counterpart on the same database before opening its repeatable-read snapshot. That session exports the snapshot for pg_dump and keeps exclusive ownership until the encrypted bundle has been atomically published. Unrelated database activity and reads can continue. File changes wait, with a bounded lock timeout; no persistent maintenance flag can strand the application after a crash.

Encrypted bytes are created before database references are committed. Deletion follows removal of live references or rollback of an unpublished upload. This ordering, combined with frozen filesystem mutations and the imported database snapshot, covers uploads whose reference commits during capture: only references visible in the snapshot are included. Unpublished orphan uploads are excluded. Future writers must preserve this ordering and use the shared gate around every filesystem mutation. Direct filesystem edits and unsupported maintenance tools must be stopped during capture.

Use direct PostgreSQL connections or a **session-mode pooler**. Transaction-mode pooling is unsupported for these session advisory locks. All API instances and the backup worker must use the same database and the same persistent/shared upload volume, with this version of the coordination code installed. A worker on another server cannot capture a local volume merely by setting UPLOAD_PATH. The dedicated SELECT-only backup login remains sufficient: the lock and exported snapshot share one session and pg_dump uses the second connection.

FILE_COORDINATION_TIMEOUT_MS defaults to 30000 and accepts 100..60000. Timeouts fail the attempt and release the owned connection. A lost coordination session aborts the dump and prevents normal publication. A killed process loses its PostgreSQL session locks automatically. Pending/incomplete artifacts are cleaned by the command; a host crash can leave an unpublished `.partial-*` file for operator inspection, never a successful archive rotation.

Ownership checks inspect the current backend's granted advisory lock and lock mode, rather than treating a live connection as proof. Legacy credential rewrites are staged and synced in a sibling temporary file, checked against the unchanged original and atomically renamed; an interrupted write leaves the original intact. A host crash may leave a hidden rewrite temporary file; inspect it under the mutation gate before removal instead of treating it as a published credential.

## File inventory and recovery

The authenticated manifest records the snapshot's table counts, required extension namespaces, each supported file reference and pending retention cleanup. Organization licenses, physician credential fields, verification documents, laboratory results, imaging reports and radiology reports must resolve to allowlisted local paths. API-relative paths and supported legacy `/uploads/` paths remain portable; absolute references are rebased into the fresh restore root. Windows source-root separators are supported. Unknown file columns, remote URLs, traversal, missing active files, symlinks, hard links and unencrypted files fail closed.

Pending retention files are included only if they still exist. A file already unlinked before its cleanup marker committed stays absent after recovery; its safe parent directory is recreated so the existing audited cleanup can resume. The backup does not revive disposed medical rows or invent successful cleanup evidence.

The existing restore command authenticates the envelope before creating fresh disposable database/filesystem targets, restores the schema and extensions, checks/rebases supported references and verifies every copied encrypted file against the manifest's size and SHA-256. Absolute medical paths are relocated inside the new restore transaction with only their named clinical-change audit trigger temporarily suspended; its original enabled state is restored before verification. This storage relocation preserves the captured clinical audit rows/head. It does not disable source triggers, foreign keys or other restored triggers. The scheduled recovery gate also verifies table counts, migration checksums and audit integrity before pruning any older B2 version. It does not need the actual application key to copy and checksum encrypted files. Preserve that key separately and perform application decryption checks during an operational recovery drill; checksum verification alone does not diagnose ciphertext that was already damaged at the source.

## Scheduling and rollout

On a worker colocated with the actual upload volume, configure **BACKUP_MODE=coordinated** and run `npm run backup:scheduled`. The existing archive encryption, private B2 scope, seven daily/three monthly retention, serialized scheduling and fresh cloud download/recovery gate are reused. Keep only one archive scheduler for this bucket/prefix; an exclusive capture lock alone does not serialize the later cloud-retention phase.

Roll out the shared-gate application and maintenance code to every writer first, drain older writer instances, verify the real volume/database connections and run a disposable capture/recovery drill. Then enable coordinated mode on the colocated scheduler. Keep the separate backup key and original application key in protected recovery storage outside B2. A rollback to writers without this gate requires stopping coordinated captures first; do not assume mixed-version writers participate in the lock.

The current hosted demonstration's GitHub worker remains explicitly **database-only** because it has no access to Render's upload filesystem. Its existing schedule is unchanged by this implementation. Uploaded-file coordination is implemented and tested on isolated fixtures; enabling it live requires deploying the new code and a worker with access to the application's persistent volume. Database-only mode continues to refuse external file references. Legacy `npm run backup` still supports a manually quiesced database-plus-file dump when writes have actually been stopped; BACKUP_QUIESCED=true does not implement coordination.
