# Clinical audit boundaries

Each HTTP request receives a server-generated request UUID in `request-context.js`. Authentication binds the verified, active user's database ID to that request's `AsyncLocalStorage` context. Caller-supplied identity headers never set the database audit actor.

`db.query` executes request-bound statements inside a transaction, including statements containing writable CTEs. `db.transaction` binds the same identity before invoking its callback. PostgreSQL `set_config(..., true)` stores the actor/request/method only for that transaction; commit and rollback discard the settings before a pooled connection is reused. Ordinary maintenance commands outside a request carry no invented application identity.

Migrations `020` and `023` add row triggers to 17 clinical and access-policy tables: `medical_records`, `diagnoses`, `prescriptions`, `lab_results`, `imaging_reports`, `radiology_reports`, `lab_orders`, `imaging_orders`, `medication_orders`, `visits`, `visit_notes`, `triage_sessions`, `care_team_assignments`, `visit_staff_assignments`, `bed_allocations`, `consents`, and `emergency_access_grants`. Nurse vital signs are medical records of type note/procedure/other and use the same trigger. Each insert/update/delete appends `clinical_change` evidence in the transaction changing that row. An audit failure aborts the change. Metadata contains resource/patient/visit/organization IDs, operation, table, request correlation and database principal; it contains no before/after clinical values.

Request-bound clinical changes require an authenticated actor. Direct maintenance changes instead retain `session_user` as the database principal, with a null application actor. These are different provenance claims and are shown as such in the evidence.

Migration `021` retains the existing advisory lock and introduces a singleton chain-head row. Its locking update forces a stale repeatable-read audit writer to fail with PostgreSQL `40001`, preserving the chain instead of appending against an obsolete snapshot. Migration `022` fixes the clinical trigger's search path, placing temporary schemas last so temporary tables cannot redirect evidence or parent identity lookups.

Migration `025` removes runtime write privileges on the head, including column grants. The narrowly scoped `chain_audit_insert` function alone advances the head with its owner's authority. It uses explicit schema names and `search_path=pg_catalog`, rejects invocation by any relation other than the retained audit table's before-insert trigger, and is not executable by runtime roles or PUBLIC. Ordinary inserts through the pre-existing audit trigger still work. This closes the earlier trigger-depth bypass: an application's own temporary trigger cannot borrow head-write rights. Runtime roles also lose audit-table trigger/truncate/update/delete privileges. Existing monitor and column-only read grants are preserved without adding insert or broader read rights.

The protected-route response audit is separate from row-change evidence. Successful JSON remains withheld until the durable append succeeds. Existing route-specific audit middleware supplies the action without installing another response wrapper. A handler may set `req.auditEventRecorded = true` only after committing a transaction that includes `logAuditEvent(logData, client)`. This marker means that the response's required event is already durable.

List responses contribute distinct valid UUIDs only from canonical server response fields `patient_id` and `patientId`. Traversal is bounded; exceeding a bound withholds the response instead of silently truncating identities. Each affected patient's trail includes the event, while filtering other patients' IDs out of the returned metadata. Unlabelled identifiers are not guessed to be patients. Binary report/credential downloads require their own durable audit before sending bytes.

Privacy export uses repeatable-read transactions and bounded serialization retries. A persistent conflict returns a retryable unavailable response after rollback. A separate response-audit outage can still cause a legacy mutation endpoint to return an error after its row has committed; the row change and its minimal evidence have already committed together. This is not a general claim that every multi-statement legacy workflow is one atomic transaction. Insurance-policy tables are outside the row-trigger list and retain their own service/request auditing paths.

The application database role has data privileges without schema administration. It can append through the existing audit insert trigger but cannot write the head or attach its own trigger to the private head-advancing function. Reprovisioning explicitly restores these restrictions after broad application data grants. A database owner who can alter schema or disable triggers remains outside this application-role integrity boundary. Hosting encryption, operational alert delivery, backup scheduling and recovery objectives are separate deployment concerns described in `monitoring-readiness.md`.

`clinical-change-audit.integration.test.js` exercises authenticated HTTP actor correlation, maintenance provenance, rollback, injected audit outages, multi-patient laboratory queues, temporary-table shadowing, repeatable-read conflict handling, head protection and full chain verification against disposable PostgreSQL.

`audit-head-privileges.integration.test.js` reproduces the nested temporary-trigger bypass inside rollback-only disposable transactions, then verifies restricted public/private-schema runtime roles, inherited default grants, ordinary audit insertion, pre-upgrade temporary triggers, provisioning repeatability and preservation of monitor/column-only permissions.

Operational logs are separate from protected audit evidence. The central logger allowlists counts, validated error codes and request correlation UUIDs; it omits human identifiers, clinical/credential payloads, SQL, raw error messages/stacks/details and process/client metadata. Level methods sanitize errors before Winston can merge their messages, and a final format also protects direct/fatal/rejection logging. Runtime EMR/visit error paths use this logger, and mail/invitation/consent reminders use constant messages without interpolated recipients. `logging.integration.test.js` captures actual JSON files and console output, including exception and rejection handlers, to verify both absence of protected fixture values and retention of operational messages/codes/counts.
