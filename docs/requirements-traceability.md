## Legal principles translated into engineering

GDPR minimization/purpose limitation informs explicit field selection, research suppression and purpose-bound authorization; accountability and breach documentation inform immutable evidence, assessment versions and notice attempts. GDPR rights are supported by authenticated information copies and review casework, not by silently deleting immutable clinical history or pretending every request is legally granted. Erasure review explicitly reports when clinical records are retained and requires an actual decision basis.

GDPR authority notice is generally due without undue delay and, where feasible, within 72 hours of awareness unless risk is unlikely; high risk can require communication to individuals. HIPAA notice obligations depend on the responsible party, breach determination, affected count and jurisdiction. Individual notices and larger HHS reports use a 60-day outer limit; smaller HHS reports use the annual rule. These distinctions are implemented as reminders and recorded decisions, not an automated legal conclusion. Sources: [EDPB breach guidance](https://www.edpb.europa.eu/sme/assess-the-risks/data-breaches_en), [GDPR official text](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng), [HHS breach notification rule](https://www.hhs.gov/hipaa/for-professionals/breach-notification/index.html).

There is no universal HIPAA clinical-record retention duration to hardcode. Retention depends on applicable law, record type, contracts and legal holds. The application retains immutable clinical evidence; reviewers record the applicable basis and actual outcome. An approved jurisdiction-specific retention/disposal policy and execution procedure remain required before actual patient data is admitted. Sources: [HHS retention FAQ](https://www.hhs.gov/hipaa/for-professionals/faq/does-hipaa-require-covered-entities-to-keep-medical-records-for-any-period/index.html), [HHS right-of-access scope](https://www.hhs.gov/hipaa/for-professionals/faq/what-personal-health-information-do-individuals/index.html).

Supabase documents default AES-256 encryption for stored customer data and TLS in transit. That provider statement supports the hosted storage design; it does not establish this organization's full compliance. Supabase separately requires a signed BAA and its HIPAA add-on for PHI use. The current free account/project has not been approved for that purpose, so the hosted demonstration remains synthetic. Sources: [Supabase security](https://supabase.com/security), [Supabase HIPAA project requirements](https://supabase.com/docs/guides/platform/hipaa-projects), [HHS cloud guidance](https://www.hhs.gov/hipaa/for-professionals/special-topics/health-information-technology/cloud-computing/index.html).

## Deployment and organizational boundaries

- The existing free Vercel/Render/Supabase deployment remains **synthetic only**. This requirement-completion branch has new migrations and must be reviewed and migrated before deployment. No actual patient records, regulator forms, outbound notices, cloud secrets or existing uploaded files were changed by this review.
- Actual patient deployment requires provider/legal arrangements appropriate to the jurisdiction, configured encrypted database volumes/backups and verified TLS, approved retention/legal-hold procedures, tested alert delivery, recovery objectives/drills, workforce/access review and an incident owner. Code cannot create a provider agreement or certify the organization.
- The new optional monitoring overlay supplies a private, authenticated scrape and an explicit Alertmanager target. It requires an owner-supplied actual receiver configuration and matching token. Its rules now use real emitted metrics; unsupported pretend business/backup counters and JSON health scrapes were removed. No cloud monitoring or message destination was provisioned automatically.
- Backups require actual write quiescence and a separately retained key. A successful synthetic local restore is evidence of tool correctness; it is not proof that the deployed host has a recurring backup or recovery process.
- Legacy unbound encrypted files intentionally fail contextual download until the reviewed, default-dry-run migration tool is applied with original ciphertext backed up. Plaintext is not silently imported.

## Verification evidence

The implementation was exercised in disposable Linux containers with synthetic principals/data, read-only source/toolchain inputs, constrained scratch storage, nonroot execution, reduced capabilities, CPU/memory/process limits and disabled external networking. The user explicitly approved downloading pinned Linux test dependencies into dependency-only images; target tests then ran offline. Existing host databases, unrelated services and cloud credentials were not used.

- Backend: 175 unit tests across 23 files and 141 Node checks across all 15 root suites passed, with zero failures or skips. The Node run used the same explicit test-discovery script as CI, with actual PostgreSQL, matching dump/restore clients and private-schema/browser checks enabled. Backend syntax checks passed too.
- Frontend: 89 behavior tests across 18 files passed. Lint, the shared-theme audit (76 stylesheets, 130 components/pages, 37 shared tokens) and the production build also passed.
- Monitoring: Prometheus `promtool` validates the production configuration and eight supported alert rules.
- Deployment configuration: the production/observability Compose files pass configuration validation with explicit synthetic inputs. Container image publication, hosted CI execution and live alert delivery were not performed by this task.
- Browser review: actual React governance screens rendered with clearly labeled synthetic local fixtures for visual/theme/responsive checks; real backend authorization/state/encryption claims come from the separate HTTP/PostgreSQL tests, not those UI fixtures.

Independent source review identified three additional defects: private-schema restore path rebasing, missing shared-list access evidence in subject exports, and a runtime-role temporary-trigger path to the audit head. All three were repaired and received regressions; the reviewer confirmed closure. A real backward-clock history regression led to monotonic evidence sequencing, and actual written-log/console/fatal tests pin the operational logging redaction boundary.

No single test run is proof against all threats. The report describes the implemented boundaries and tested cases rather than promising absolute privacy, uninterrupted availability or legal compliance.
